# Контракт Iapetus

Агент — Claude Code, Codex CLI или Antigravity CLI — живёт в контейнере Docker (session), а его окружение — машина
runner: файлы, команды и MCP проекта выполняются на ней. Исключение — MCP server (инструменты Iapetus). Две
программы на Rust: **orbit** (`server`, `session`) и **waldo** (`worker`, `runner`). Работу выполняет только waldo
runner.

## Роли

- **orbit server** запускается в Docker и ждёт внешних подключений.
- **orbit session** ждёт, пока её разбудит waldo runner: его назначает server по запросу waldo worker.
- **waldo worker** получает CLI-доступ к harness агента на orbit session.
- **waldo runner** ждёт, когда orbit session пришлёт ему работу.

| Роль | Где | Что делает |
|---|---|---|
| orbit `server` | один на систему, свой контейнер | Координатор без интерфейса для человека; управляется запросами worker по каналу управления (SSH), для агента — MCP-сервер. Центр сертификатов SSH, токены, регистрация runner, окружение и документы, реестр, точка входа ssh. Поднимает, восстанавливает, удаляет контейнеры session, обновляет агентов |
| orbit `session` | контейнер на хосте server | Одна сессия агента в pty; агент запускается без учётных данных, пользователь входит сам; меняет resume по указанию server. Принимает ssh-вход в TUI. Перехватывает действия агента и шлёт на runner |
| waldo `worker` | машина пользователя | Единственный терминал управления, только TUI, без личности: по `orbit_key` обращается только к server. Поднимает и убирает session, входит в них по ssh; выбирает, переключает, переименовывает runner, создаёт временные; отзыв runner, новый `orbit_key` |
| waldo `runner` | каждая машина, где идёт работа | Единственный узел с личностью (fingerprint, ключ узла, сертификат). Выполняет задачи session в рабочем каталоге, по запросу server создаёт временные runner; окружение команд — от server, `.env`, системы |

```
waldo worker, runner × N ──канал управления: SSH──► orbit server (CA, реестр, окружение, документы, MCP) ◄──канал управления── orbit session × N
waldo worker ──ssh -J──► orbit session × N (агент, FUSE, оболочка, шлюз)
waldo runner × N ──канал данных: SSH через jump (файлы, команды, watch)──► orbit session
```

- Server — в своём контейнере; внешний SSH слушает только адрес сети Tailscale или ZeroTier, внутренний (для
  session) — сеть Docker. Worker входит через `ssh -J` по server, порты сессий наружу не открыты, сеанс шифруется до
  session.
- Через server идёт только управление; данные ходят между session и runner по SSH-каналу, который runner
  устанавливает через jump (server видит шифротекст).
- Вся система — в отдельном rootless Docker под непривилегированным пользователем (`CAP_SYS_ADMIN` без
  AppArmor/SELinux равен root хоста; в rootless побег даёт только этого пользователя). Docker доступен только
  server, через свой прокси на Rust: он разбирает тело `POST /containers/create` и сверяет со шаблоном сессии (образ
  по digest, точный набор capabilities, устройство только `/dev/fuse`, без bind и `host`-режимов, лимиты, метка
  `iapetus.role=session`), пересобирает тело, лишнее поле — отказ; операции только над контейнерами с меткой (кроме них — `ping`, список, `inspect`, `logs`, `wait`, `inspect` и удаление тома);
  `exec`, `attach`, `archive`, `build`, `commit`, тома с `DriverOpts` запрещены.
- Runner и session никогда не на одном устройстве или в одном контейнере.
- Контейнер — один агент, его закрепляет server (метка тома `iapetus.agent`); worker по ssh видит только его интерфейс.
  Том состояния один и монтируется в каталог состояния этого агента под `/home/agent` (`nerve::agent::AGENT_ROOT`:
  `.claude`, `.codex` или `.gemini`, по метке `iapetus.agent`; без метки или с неизвестным агентом — отказ): пересоздание
  продолжает разговор через `resume`. Пользователь образа — `agent`, каталоги всех агентов в образе принадлежат ему
  (иначе том получил бы владельца root). Claude Code — с `CLAUDE_CONFIG_DIR=/home/agent/.claude` из профиля (иначе
  `.claude.json` вне тома).
- До запуска Claude Code агент session сливает в `.claude.json` ключи `hasCompletedOnboarding`,
  `hasSeenAutoDefaultNudge`, `hasSeenAutoDefaultNotice`, `projects["/"].hasTrustDialogAccepted` и при каждом запуске —
  `projects[<путь проекта>].hasTrustDialogAccepted` (прежний отказ из тома перезаписывается); в `settings.json` —
  `permissions.defaultMode: "bypassPermissions"`, `skipDangerousModePermissionPrompt: true`. Claude Code (2.1.285,
  2.1.288) берёт доверие по предкам каталога только вне git-репозитория: в репозитории и его worktree поиск
  останавливается на корне, и без ключа пути проекта агент спрашивает доверие с ответом «нет, выйти» по умолчанию.

## Состояния session

Server поднимает session только по запросу worker (новое подключение), удаляет только по запросу («Завершить
сессию»); сессий без запроса и резерва нет. Восстановление — пересоздание контейнера с тем же томом и `resume`:
само, если контейнер пропал; из `failure` — по запросу worker.

| Состояние | Значение | Переходы |
|---|---|---|
| `success` | работает штатно | `warning`, `waiting` (401/403, плановая остановка агента), `failure` |
| `waiting` | ждёт авторизации агента | `success`, `failure` |
| `warning` | ошибки, работа приостановлена | `success`, `waiting` (ключ недействителен), `failure` |
| `failure` | агент падает сразу после перезапуска, нужен человек | `waiting` (перезапуск: та же сессия и разговор) |

Состояние определяет агент session по событиям шлюза, процессу агента и каналу данных; шлёт server
запросом `Status` при каждой смене (причина, время сброса лимита); server хранит в реестре, показывает в
TUI и `session_status`. Запущен ли агент в pty (`agent_running`), session сообщает в том же `Status`; server держит
значение в памяти, пока канал управления session открыт: по нему `Sessions.Start` отвечает `Ready`, а jump пускает
worker.

| Событие | Состояние | Обратно |
|---|---|---|
| контейнер поднят, runner не подключён | `waiting` «ждёт runner» | runner подключился — агент запускается |
| агент запущен | `waiting` | первый ответ 2xx сервиса (Claude Code, Antigravity — проба квоты; Codex — первый ход) → `success` |
| 401/403 на запрос API модели (Claude Code — только `/v1/*`; Gemini API ещё 400 `API_KEY_INVALID`) | `warning` → `waiting` «нужен вход» (`Cause::LoginRequired`) | пользователь вошёл — первый успешный ответ возвращает `success`; агент не перезапускается |
| исчерпан лимит подписки | `warning` + время сброса: Claude Code `anthropic-ratelimit-unified-*-reset`, Codex `x-codex-*`, Antigravity `retryDelay`/`resetTime` | 2xx на основной ход → `success` |
| контекст переполнен (основной ход) | `warning`: сжатие или новый разговор | 2xx на основной ход → `success` |
| ошибка соединения | `warning` «нет соединения» с первой неудачи | соединение вернулось → `success`; после пятой попытки агент получает 502, остаётся `warning` |
| runner пропал | `warning` | runner в сети → `success` |
| runner не вернулся за 5 минут или назначение снято | `waiting` «нужно назначить runner»; процесс агента завершён планово | worker назначил runner → агент запускается (с `resume` или чисто — выбор worker) |
| процесс агента завершился без указания server (`/exit`, падение) | session сразу запускает агента заново с флагом продолжения профиля (Claude Code `--continue`, Codex `resume --last`, Antigravity `-c`): `waiting` «агент перезапущен» (`Cause::AgentRestarted`) | первый принятый сервисом запрос нового процесса → `success` |
| нет сохранённого разговора для пути проекта (`/exit` до первого сообщения; Claude Code 2.1.288 с `--continue` пишет «No conversation found to continue» и выходит с кодом 1) | профиль запускает агента без флага продолжения (Claude Code: нет `*.jsonl` в каталоге разговоров проекта; путь длиннее предела или ошибка чтения — с продолжением; Codex и Antigravity — всегда с продолжением: формат не снят) | — |
| третий такой выход за 60 с | `failure` «агент завершается сразу после запуска, перезапуск остановлен» (`Cause::AgentExited`) | `f` в TUI → `waiting` |

- В `waiting` ошибки остаются `waiting` с причиной. `failure` — только повторяющийся выход процесса агента без указания server;
  плановый выход (перезапуск Codex через `resume`, обновление агента) — не `failure`.
- Ошибка основного хода, которую агент не повторяет (Codex — прочие 429; Antigravity — 400, 500), — `warning` до
  2xx на основной ход.
- Не меняют состояния: ограничение частоты, 5xx и обрыв потока, если агент повторяет; прерывание; ошибки служебных
  запросов, кроме отказа учётных данных и лимита (последняя видна в статусе).
- Занятость (запросы субагентов и сжатий) — по виду запроса из шлюза, снимается с концом запроса; конец хода
  считается только по основному агенту.

## Выбор runner

| Значок | Состояние |
|---|---|
| 🔓 | свободен: в сети, session с ним нет |
| 🔒 | занят: в сети, с ним работает session |
| 📴 | нет в сети: нет канала управления |

- Состояние ведёт server: runner в сети, пока открыт его канал управления (подробности — «Присутствие и
  переподключение»); обрыв без закрытия TCP ловит keepalive SSH (5 с × 3). Канал данных назначенной сессии при
  обрыве останавливается так же быстро — keepalive, 15 с.
- Назначение при пропаже не снимается: session в `warning` и агент жив, вернётся в `success`, когда runner в сети. Агент не
  работает без runner — это его окружение: если runner не вернулся за 5 минут (отсчёт ведёт server по присутствию канала управления runner) или worker снял
  назначение, session по указанию server планово завершает процесс агента (не `failure`), контейнер живёт. Агент снова запускается только по назначению
  worker: тот же runner или новый, `resume` — выбор worker; вернувшийся сам по себе runner агента не поднимает.
- Личность — только у runner и его клонов (fingerprint, uuid4, неизменяемый; server закрепляет за ключом узла).
  Владельцев и пользователей нет. Fingerprint session задаёт server (`--session`).
- Имя — только подпись: worker переименовывает запросом к server, `--name` — начальное; окружение и кэш на fingerprint.
- Runner выбирается при подключении в TUI; переключают его session (MCP) и worker (по имени). С runner работает
  одна session.
- Рабочий каталог — аргумент, иначе каталог запуска. Он не может совпадать с путями контейнера, лежать в них или
  содержать их (FUSE монтируется по тому же пути): `/bin`, `/sbin`, `/lib*`, `/usr`, `/etc`, `/opt`, `/dev`, `/proc`,
  `/sys`, `/run`, `/tmp`, `/var`, `/work`, `/home/agent` (каталоги состояния всех агентов); `/` — отказ. Ту же проверку
  (`nerve`, общая функция) повторяет session при назначении: плохой путь — ошибка назначения, пара откатывается.

### Временные runner (клоны)

- Клон — временная точка входа в другой каталог той же машины, а не работа с git. Создаёт runner по запросу server
  (от session или worker); каталог не совпадает с родительским и не вложен в него. Клоны не создают клонов.
- Корень git-репозитория — клон в `git worktree` на своей ветке. Иной каталог (в том числе подкаталог репозитория) —
  просто точка входа: без ветки, автокоммита и уборки.
- Свой fingerprint; имя — имя каталога клона: клон репозитория — `<каталог>-clone-<N>` на ветке `iapetus/<имя>`.
  Приоритет окружения: свои, родителя, `all`; `.env` — из каталога, указанного в запросе.
- Зависит от своей session, не от родителя. Создаётся заранее; без назначения за 5 минут завершается; worktree и ветка остаются (см. ниже).
- Конец клона — конец или переключение session (обрыв канала не трогает). Worktree: незакоммиченное коммитится в
  ветку клона с пометкой автокоммита, затем worktree удаляется, ветка остаётся. Автокоммит не удался — worktree
  всё равно удаляется, потерянные пути (с `.gitignore`) — ошибкой в журнал. Ветка сменена — не коммитит и worktree не
  трогает. Клон без git — каталог не трогается. Клон, у которого не было session (нет автора), не коммитит и worktree
  не трогает.

### Автор коммитов

- Только от заданного пользователя: из `.env` каталога запуска worker (`--env-file`, `IAPETUS_ENV_FILE`), иначе пользователь по умолчанию из настроек orbit.
  Runner на время сессии ставит `GIT_AUTHOR_*`, `GIT_COMMITTER_*` (NAME, EMAIL) выше слоя server, `.env`, системы: так идут
  коммиты агента и автокоммит клона.
- `GITHUB_TOKEN` из того же `.env` worker передаёт в `Sessions.Start`; server хранит его и автора в реестре
  зашифрованно и шлёт runner в `Start` — при назначении и после переподключения runner. На runner — в памяти,
  маскируется в выводе; на `End` пары фоновые процессы её команд убиваются, токен уходит вместе с ними.
- Назначение выбирают worker или session (MCP `runner_use`); runner сам к сессии не назначается. Смена runner — без
  пересоздания контейнера: server проверяет runner (в сети, свободен, не отозван), записывает пару и шлёт session
  `AssignRunner`; session завершает агента, переключает канал данных и FUSE (кэш и метаданные прежнего runner
  сбрасываются; другой путь проекта — lazy detach прежней ФС и монтирование по новому, пустые предки создаются и
  остаются) и запускает агента заново; `resume` указывает назначающий (worker; для `runner_use` — 
  продолжение разговора). Проверка не прошла — прежняя пара остаётся, ошибка — тому, кто выбирал.

## Вход через TUI worker

TUI — терминальное меню worker: список session, новое подключение с выбором агента и runner, узлы, окружение. Родной интерфейс агента работает в pty session, worker подключается к нему зрителем; своего TUI поверх headless-режима агентов нет и не планируется.

1. **Session.** Имя, агент, состояние с причиной; «Новое подключение».
2. **Новое подключение.** Агент (Claude Code, Codex CLI, Antigravity CLI), затем runner. Вход в агента — вручную в его
   терминале после подключения.
3. **Runner.** Значок, имя, fingerprint; выбирается только 🔓.

Отдельные разделы TUI: узлы — список и отзыв runner, новый `orbit_key` (`N`), окружение (`E`).

- Клон worker создаёт запросом `Runners.Clone` к server, server шлёт runner `Clone` (как
  для `runner_clone`); на 🔓 и 🔒, не на 📴; runner не занимает и session не прерывает. Пункт списка runner в TUI;
  CLI для скриптов нет; команд на runner worker не выполняет; runner принимает `clone` только от server.
- Любой worker с действующим `orbit_key` пользуется любым runner и session. Для `waiting` «нужен вход» — подключиться
  к session и войти в агента заново.
- Сертификат worker — на одноразовый ключ запуска, принципалы `iapetus-control`, `iapetus-jump`, `name`; `permit-pty` —
  для входа в сессию через jump; продлевается пока worker работает. Сертификат runner pty не разрешает.
- tmux нет: агент session держит pty и подключает к нему канал входящего worker. Вывод — всем, ввод — от любого,
  окно — наименьшее из подключённых.
- Новому зрителю — экран из копии агента (`vt100`): `state_formatted` под той же блокировкой, что подписка на вывод,
  плюс заголовок (`OSC 0`) и `?1004h`; истории выше экрана нет. Зрителю с окном выше pty — область прокрутки высотой
  pty (`CSI 1;<строк>r`) при подключении и смене размера. Ответы терминалов на DA1, XTVERSION, kitty keyboard в pty не
  пересылаются.
- Session принимает worker под логином `name`: `key_id` сертификата — worker, `name` среди принципалов и не служебный
  (`iapetus`, `iapetus-…`). Pty и `shell` получает только сертификат с `permit-pty`; канал один на соединение, `exec` и
  переменные окружения отвергаются.
- Вход возможен, пока в session запущен агент (`Status.agent_running`): иначе jump отказывает worker. Зритель, отставший
  больше чем на 1024 куска вывода, отключается; введённое сверх 1 МиБ, пока агент не прочёл, отбрасывается. Без зрителей
  pty остаётся прежнего размера (начальный 80×24).
- Выход из агента — Ctrl-]; остальные байты, включая Ctrl-C, идут агенту. Выход или обрыв закрывает только канал: pty и
  агент живут.
- Настройки worker — только файл (`--settings`, `IAPETUS_WORKER_SETTINGS`; по умолчанию
  `$XDG_CONFIG_HOME/iapetus/worker.conf`, иначе `~/.config/iapetus/worker.conf`) с правами не шире `0600`: строки
  `ключ = значение`, `#` — комментарий, повтор и неизвестный ключ — ошибка. `orbit_url`, `orbit_ca` (сам открытый ключ
  OpenSSH, не путь) и `orbit_key` обязательны, `name` — по умолчанию локальный пользователь. Флагов и переменных для них
  нет.
- Журнал worker — `worker.log` рядом с файлом настроек (`0600`, дописывается): экран занят TUI.
- `a` в списке сессий — перезапустить агента выбранной сессии с продолжением разговора: первое нажатие ждёт конца
  хода (`restart_pending` в `Status` и `SessionInfo`, в колонке «Причина» — «перезапуск ждёт конца хода»; состояние
  и причина не меняются), повторное — сразу. Перезапуск по требованию плановый: не `failure` и не в счёт «3 выхода
  за 60 с». Флаг снимается остановкой, выходом агента или запуском.
- Агент перезапущен или вышел — терминал агента закрывается, worker возвращается в список с сообщением («агент
  перезапущен: Enter — войти снова»). Enter на сессии без запущенного агента вход не открывает: TUI показывает
  состояние и подсказку (`f` — перезапустить с продолжением, `e` — завершить; без runner — `R`, `e`).
- Журналы (info): server — смена состояния session с причиной, запуск и остановка агента, запросы worker на
  завершение и перезапуск, закрытие канала управления session с причиной, подтверждение `End` от runner; runner —
  остановка команд сессии и конец обслуживания канала данных.
- Журнал session переживает контейнер: перед удалением (завершение, перезапуск из `failure`) server сохраняет
  stdout и stderr контейнера в `<data-dir>/session-logs/<fingerprint>-<секунды Unix>.log` (`0600`, каталог `0700`):
  20 последних файлов на server, у каждого хвост до 16 МиБ по границе строки; сбой сохранения удалению не мешает.

## Управление server

- Все равны: прав по лицам нет, любой worker с действующим `orbit_key` управляет всем.
- `orbit_key` один на систему (регистрация и продление runner, вход worker). В пустом реестре server создаёт первый в
  файле `orbit_key` (`0600`) каталога состояния: в нём один секрет и перевод строки, без пояснений. Файл удаляется
  после первого использования ключа — регистрации runner, сертификата worker или выдачи нового ключа. Новый
  `orbit_key` — из TUI, отдаётся в ответе один раз, в журнал не пишется, отменяет прежний.
- Граница доверия (решение пользователя, принято): runner хранит `orbit_key` в каталоге личности, и команды агента на
  runner его читают — от того же пользователя ОС. С ним агент регистрирует новый узел и входит на server как worker;
  `runner_clone` принимает `$HOME` runner. Агент на runner обладает правами пользователя Iapetus; защита — доверие к
  агенту и отзыв ключа из TUI.
- Управление — запросы `Sessions.*`, `Runners.*`, `Nodes.*`, `Env.*` по каналу управления только от worker
  (по роли сертификата): session, список и отзыв runner, `orbit_key`, окружение. Своих команд и интерфейса у server нет.
- Состояние — SQLite (узлы, fingerprint, занятость и назначения, сертификаты, окружение). Значения окружения и токен
  GitHub зашифрованы; ключ шифрования и закрытый ключ CA SSH — отдельные файлы `0600`.
- MCP-сервер для агента в session — server: агент ходит к нему напрямую по внутренней сети Docker (HTTP, путь `/mcp`
  на `--mcp-listen`) со своим токеном MCP (токен одной сессии действует только на неё). Токен — `<fingerprint>.<HMAC>`
  на ключе `mcp.key`: server его не хранит, токен переживает перезапуск server и контейнера; запрос без действующего
  токена отклоняется до MCP, сессия, удалённая из реестра, теряет доступ. Инструменты: `runner_list` (имя, fingerprint,
  состояние, временный ли), `runner_use` (переключить на свободный runner), `runner_clone` (клон текущего runner в
  каталоге), `session_status` (состояние, runner).

имеют права `0600`; шире — отказ запуска. Лимиты контейнера равны верхним границам шаблона прокси.

## Права в контейнере session

- `/dev/fuse`, `CapDrop=ALL`, ровно `SYS_ADMIN` (mount FUSE), `SETUID`, `SETGID`, `SETPCAP`; `no-new-privileges`
  обязателен. tmpfs ровно два: `/work` (`noexec,nosuid,nodev,mode=0700`, размер при создании) и `/run/secrets`
  (`size=1m`, файл токена). Хост с AppArmor: профиль `docker/apparmor/iapetus-session` (`docker-default` +
  `mount fstype=fuse`).
- Агент orbit стартует root, монтирует FUSE с `allow_other` (точка вне `/home/agent`) и остаётся root с
  `CAP_SYS_ADMIN` для размонтирования. Агента запускает однопоточный дочерний процесс: лидер сессии с pty, снимает
  `CAP_SYS_ADMIN` из bounding set, чистит inheritable, ставит `no_new_privs`, сбрасывает группы, `setresgid`/
  `setresuid`, `exec`; после смены uid размонтировать FUSE нельзя. Конфиги агента пишет session от root до
  понижения и передаёт их агенту через `chown`, сокет оболочки передан готовым. Крейт `rustix`, без `unsafe`.
- fuser монтирует через `mount(2)`: `fusermount3`, fuse3, `/etc/fuse.conf` не нужны; seccomp Docker не мешает.
- В образе только агенты и агент orbit, инструментов разработки нет.
- Метки: контейнер — `iapetus.role=session`, `iapetus.session=<fingerprint>` и `iapetus.agent` (по ней прокси выбирает каталог тома); том `iapetus-state-<fingerprint>` — те
  же и `iapetus.agent` (`claude`, `codex`, `antigravity`), `iapetus.work` (размер `/work`, байты). Контейнер, потерянный
  без запроса worker, server пересоздаёт на этом томе; агент и размер `/work` берёт из меток тома.
- Окружение контейнера задаёт server, только `IAPETUS_*` (прокси другого не пропускает): `IAPETUS_SESSION`
  (fingerprint сессии), `IAPETUS_ORBIT_URL`, `IAPETUS_AGENT` (обязателен, умолчания нет), `IAPETUS_RUNNER`, `IAPETUS_MCP_URL`,
  `IAPETUS_MCP_TOKEN`, `IAPETUS_RESUME=1` — продолжить разговор (Claude Code `--continue`, Codex `resume --last`,
  Antigravity `-c`; при пересоздании). Секреты — значениями в `IAPETUS_SESSION_SECRET_CONTENT` (секрет входа на server),
  `IAPETUS_DATA_HOST_KEY_CONTENT`, `IAPETUS_DATA_HOST_CERT_CONTENT` (хост-ключ и сертификат канала данных),
  `IAPETUS_CA_PUBLIC_KEY_CONTENT` (CA); session пишет их в `/run/secrets/*` (`0600`). Учётных данных агента среди них нет. Каждый запуск контейнера выдаёт новый секрет входа, прежний перестаёт
  действовать. Агент запускается с очищенным окружением: только `PATH`, `LANG`, `LC_*`, `TZ`, затем переменные
  состояния из перечня изоляции профиля и остальные переменные профиля (в том числе `IAPETUS_SHELL_CALLS`: `claude` или
  `plain`, вид вызовов оболочки; без неё оболочка отказывает); прокси и сертификатные переменные в него не попадают.

## Агент в коробке

FUSE, подменённая оболочка и шлюз одни для всех агентов; различия — профиль агента внутри orbit.

Агент — «Docker наоборот» (решение пользователя): по умолчанию harness видит и меняет окружение runner, а не своё.
Дисковые операции агента перехватываются и исполняются на runner, результат возвращается агенту; `pwd` и пути
проекта — как на runner (FUSE монтируется по пути проекта на runner). Конфигурация агента — на session, конфигурация
проекта — на runner;
в изоляции контейнера остаётся только перечень, который объявляет профиль агента: каталог конфигурации и учётных
данных, собственные сетевые вызовы агента, его бинарник и системные файлы, без которых он не запустится. Общий код
перечень только применяет. hostname, `/etc/os-release` и путь `$HOME` агент видит как на runner; конфигурация агента
при этом остаётся в контейнере (`CLAUDE_CONFIG_DIR`, `CODEX_HOME` вне `$HOME`; у Antigravity — ссылка `$HOME/.gemini` в
каталог состояния).

- `$HOME` runner (решение пользователя): runner отдаёт его (`--home on|off`, `IAPETUS_HOME`, по умолчанию `on`; клон
  наследует), session монтирует второй FUSE по каноническому пути `$HOME` запросами `Root::Home` — чтение и запись
  как в проекте. Монтируется до проекта, отсоединяется после; проект внутри `$HOME` — поверх каталога FUSE `$HOME`;
  `$HOME` внутри проекта или равный ему, `--home off`, незаданный или пересекающийся с путями контейнера `$HOME` —
  без второго FUSE (`$HOME` агента — каталог контейнера). Смена `$HOME` или его отдачи перезапускает агента.
  Запретов нет, кроме `~/.claude` runner (конфигурация агента — на session): `EACCES` по тексту пути, по настоящему
  пути открытого файла и в `ReadLink`; в `ReadDir` корня `$HOME` записи нет, события watch по ней отбрасываются.
  Предки проекта внутри `$HOME` (`~/CLAUDE.md`) агент читает как на runner. FUSE проекта монтируется с
  `DefaultPermissions`, FUSE `$HOME` — без: `$HOME` обычно `0700`, его файлы видны принадлежащими агенту, и session
  (root без `CAP_DAC_OVERRIDE`) не создала бы и не смонтировала проект внутри; права в `$HOME` проверяет runner своим
  пользователем. Личность runner в `$HOME`
  (`~/.local/state/iapetus`) агенту видна — как и через Bash.
- `RunnerHost` несёт канонический `home`, `home_origin` (исходная запись, если отличается) и `home_served`. Если
  `$HOME` runner — ссылка, session ставит в контейнере ссылку с исходного пути на канонический (вне системных
  каталогов, корня состояния и проекта; настоящий каталог не затирается).
- Записи перечня изоляции профиля (`Isolation.home_links`; Antigravity — `.gemini`) FUSE `$HOME` отдаёт сам ссылками в
  каталог состояния поверх одноимённых записей runner; создать, удалить, переименовать их нельзя (`EIO`). Без FUSE
  `$HOME` — прежние ссылки в каталоге контейнера. `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_CONFIG_HOME`,
  `XDG_STATE_HOME` агента — `<каталог состояния>/xdg/{data,cache,config,state}`.
- В FUSE `$HOME` первое обращение к каталогу читает его целиком (`ReadDir` + watch), промахи `lookup` отвечает кэш
  эпохи; у каждого корня свой `Workdir` и `Watcher` на runner; предзагрузка шлюзом выбирает FUSE по самому длинному
  префиксу пути. Правила Iapetus: файлы в `$HOME` встроенные инструменты видят как на runner, `.claude` закрыт,
  остальное вне проекта — контейнер, читать через Bash.
- Символическая ссылка (`ReadLink`) отдаётся как есть, если цель внутри `$HOME` или проекта; цель вне них — `EACCES`:
  ядро разрешило бы её в файловой системе контейнера и показало агенту чужой файл под видом файла runner.

- Runner шлёт окружение (`RunnerHost`: путь проекта, hostname, `/etc/os-release`, `$HOME`) первым запросом `Host`;
  session получает его в `AssignedRunner.host` и до запуска агента: проверяет путь, ставит hostname (`sethostname` в
  своём UTS-пространстве, `CAP_SYS_ADMIN` шаблона; строка `127.0.0.1 <имя>` в `/etc/hosts`), пишет `/etc/os-release`
  файлом (пустой или больше 16 КиБ — не меняется), создаёт `$HOME` (root, `1777`: у session нет `CAP_CHOWN`) и монтирует
  FUSE по пути проекта. `$HOME` runner, который пересекается с системными путями, лежит в проекте, не абсолютный или
  закрыт агенту, заменяется корнем состояния `/home/agent` — назначение не отклоняется. Агент без назначения не
  запускается; cwd агента — путь проекта.
- Смена пути проекта переносит разговор: маркер `<каталог состояния>/iapetus-project` хранит прежний путь, профиль
  переносит разговоры под новый. Claude Code (2.1.288) — `<CLAUDE_CONFIG_DIR>/projects/<путь>`, где каждая единица
  UTF-16, кроме `[A-Za-z0-9]`, заменена на `-`; пути длиннее 200 знаков не переносятся (Claude Code добавляет хеш).
  Codex и Antigravity не переносят (не проверено).

Код агентонезависим (решение пользователя): первый релиз проверяет только Claude Code, Codex CLI и Antigravity CLI
подключаются в версии 2.0 без переделки общих частей. Имя конкретного агента допустимо только в его профиле и в
разборщиках его провайдера; протокол, реестр, параметры командной строки, обновление агента, лимиты, TUI и журналы
говорят об «агенте» и различают агентов значением `Agent`.

- Профиль на трёх уровнях: `nerve::agent` (идентификатор, имя, каталог состояния, `AGENT_ROOT`), server
  (`server/update/<агент>.rs` — источник выпусков) и session (`session/agent/<агент>.rs` — окружение, файлы, правила,
  перечень изоляции, обновление). Общий код применяет то, что объявил профиль.
- Перечень изоляции (`Isolation`): переменные состояния (`CLAUDE_CONFIG_DIR` и аналоги), пути проекта, скрытые в FUSE,
  шаблон временных файлов агента, которые до `rename` остаются в контейнере (без шаблона всё уходит на runner), адрес
  API подписки и программа агента. Предел длины имени MCP-инструмента — тоже из профиля.
- Разбор вызовов оболочки Claude Code — в его профиле (`shell/call/claude.rs`); вид вызовов задаёт профиль.

## Перехват в session

Встроенные инструменты не отключаются, хуки не используются.

1. **FUSE** — файлы. Рабочий каталог — файловая система session; содержимое с runner.
2. **Подменённая оболочка** — команды. Служебные вызовы Claude Code (`-c env`, снимок окружения) выполняются
   локальным bash; вызов команды идёт на runner, cwd runner пишется в файл, откуда Claude Code берёт каталог.
   Встроенные Grep и Glob на Linux выключены: поиск идёт через `find`/`grep` в Bash, то есть на runner.
3. **Шлюз** на базовом адресе API — только наблюдение: пересылает без изменений, выдаёт события для FUSE и оболочки.
   Инструкции runner (rules, skills, `CLAUDE.md`/`AGENTS.md`) идут файлами через FUSE, не шлюзом.

### FUSE

- Читаемые файлы — в `/work` (плоский список кэш-файлов в tmpfs, исчезает при остановке): имя
  `sha256(<fingerprint runner>:<полный путь>)` + расширение; агент видит настоящие пути. Чтение только из копии.
- Файла нет в кэше — скачивается без проверок. Есть и обращение новое (первый `open` после команды или конца хода;
  Edit открывает файл до 6 раз) — хеш сверяется с runner, расхождение — скачивание.
- **Запись — в момент `rename`.** Временный `<имя>.tmp.<pid>.<hex>` остаётся в контейнере; на `rename` поверх цели
  session одним запросом шлёт содержимое и хеш версии, которую видел агент (новый файл — «не существует»). Runner под
  блокировкой пути сверяет хеш, пишет временный файл рядом, `fsync`, `rename`. Отложенной записи нет: «updated
  successfully» — после записи на runner, поздний конфликт невозможен, падение контейнера правок не теряет.
- Внешняя правка до записи обнаруживается; запись между сверкой и `rename` теряется, как у агентов на диске (POSIX
  не даёт атомарной проверки). Убийство агента, пишущего на месте, между `O_TRUNC` и `write` оставляет пустой файл и
  на runner.
- **Конфликт** (хеш не совпал) — `ECANCELED` из `rename` (`ECANCELED: operation canceled, rename '<tmp>' ->
  '<цель>'`), файл на runner не меняется; ту же проверку проходят `open` с `O_WRONLY` и `setattr size`. После
  конфликта копия, метаданные и список каталога устаревают.
- Запрет: при записи возвращать `EPERM`, `EBUSY`, `EEXIST`, `EXDEV`, `EACCES` из `create` (Claude Code молча
  перезаписывает цель на месте) и `EINTR` (бесконечный повтор).
- Версия, которую видел агент, — хеш прочитанного или записанного либо «файла нет» (после `ENOENT`); не видел —
  то, что на runner в момент записи. При `rename` поверх inode переносится на путь оригинала. Созданные файлы
  принадлежат uid/gid вызывающего (иначе `fchmod` падает).
- **Атрибуты** — TTL 0 из локального кэша метаданных, который обновляют события watch. TTL > 0 ломает защиты Claude
  Code (Write стирает внешнее изменение, Read после конфликта получает «file unchanged»). `lookup` несуществующих
  путей — тоже из кэша (иначе запросов в 10–30 раз больше).
- **Эпоха.** Метаданные и список каталога верны в пределах эпохи; новую начинают «команда выполнена», «конец основного
  хода», пропуск событий; тогда ответ кэша идёт к runner. Внутри эпохи — события watch и собственные изменения. Копия
  помнит атрибуты, при которых совпадала: изменились — следующий `open` сверит хеш.
- Каталог без наблюдения (`ReadDir` с `watched: false` или `Unwatched`) не кэшируется, его файлы сверяются на каждом
  `open`, пока `ReadDir` не поставит его под наблюдение; доверие решает ответ `ReadDir`, а не порядок сообщений.
- Временный файл профиля Rename — имя `\.tmp\.\d+\.[0-9a-f]{12}$` в любом каталоге (включая `.claude/.cc-writes/`);
  другие `.tmp.` — обычные файлы. Осиротевшие остаются в контейнере. Файл, созданный сразу под своим именем,
  пишется на месте и уходит на `flush` (профиль `Flush`).
- `Rename` файла runner; `ENOTSUP` — каталоги, ссылки, `RENAME_NOREPLACE`/`RENAME_EXCHANGE`, перенос поверх
  временного. `setattr` права, владельца, время не меняет (`ENOTSUP`, Claude Code игнорирует). Цель ссылки не читается.
- Предел файла — размер `/work`, не больше 1 ГиБ (`--max-file`, `IAPETUS_MAX_FILE`): больше — чтение `EIO`, запись и
  `truncate` `EFBIG`. Файл идёт одним сообщением (кадрами канала), собирается в памяти.
- Запрос к runner ждёт ответа 30 с и ещё секунду на каждые 4 МиБ запроса и ожидаемого ответа: файл в гигабайт не
  упирается в таймаут одного запроса.
- Колбэки fuser синхронные, агент отвечает из задачи tokio. Раз в минуту операция FUSE запускает очистку копий без
  обращений больше 2 часов; запись о версии агента не удаляется.
- Правила Iapetus: fingerprint, имя и ОС текущего runner, имена его переменных окружения (или «runner не назначен»), смысл `ECANCELED` (перечитай и повтори) и
  документы server. Файл один (модуль `rules` session), вне FUSE, root, `0644`: session
  пишет его до запуска агента и заменяет через `rename` при смене runner и документов (подписка `Docs`), одинаковый
  текст не пишется заново. Claude Code — `/etc/claude-code/.claude/rules/iapetus.md` (заметка «changed on disk»,
  `--resume` на границе хода приносит разницу); Codex — `~/.codex/AGENTS.md` (каждый запрос к модели); Antigravity —
  `~/.gemini/config/rules/iapetus.md`, `trigger: always_on` (со следующего хода). Результат `runner_use` сам
  описывает новый runner.
- Правила вступают при запуске агента. Агент перезапускается при смене runner и по прямому требованию worker из TUI
  (с продолжением разговора): первое требование ждёт границы хода, повторное, пока перезапуск ожидает, перезапускает
  сразу и обрывает текущий ход; смена документов server и `instructions` проектных MCP агента не перезапускает: Codex и
  Antigravity увидят правку сами, Claude Code — после перезапуска. Правила содержат путь проекта на runner (тот же путь
  видит агент, команды исполняются в этом каталоге) и подсказки: `rg` на runner может отсутствовать — использовать
  `grep`; файлы вне проекта читать через Bash (`cat`, `grep`), встроенные инструменты чтения и поиска их не видят.

### Шлюз

| Событие | Claude Code (Messages) | Codex (`--gateway-api responses`) | Antigravity (`--gateway-api gemini`) |
|---|---|---|---|
| Конец хода | `stop_reason: end_turn` | `response.completed` без вызовов инструментов и `end_turn: false` | `finishReason: STOP` без `functionCall` |
| Вызов инструмента | `tool_use` | `output_item.done`: `function_call`, `custom_tool_call` | `functionCall` |
| Прерывание | поток оборван клиентом | `response.incomplete` `interrupted`; обрыв | обрыв |
| Лимит подписки | 429 с `anthropic-ratelimit-unified-status: rejected` (не повторяется) | 429 `usage_limit_reached` | 429 с `QuotaFailure` или `retryDelay` > 30 с |
| Ограничение частоты | 429 без `rejected` (до 10 повторов) | `response.failed` `rate_limit_exceeded` (прочие 429 — ошибка основного хода, `warning`) | прочие 429 |
| Контекст переполнен | 400 «prompt is too long» | `response.failed` `context_length_exceeded` | 400 «exceeds the maximum number of tokens» |

Ошибка соединения — нет соединения с API; конец сессии — выход процесса агента (знает session, не шлюз).

- `EndTurn` — только по основному ходу. Служебные запросы (субагент, заголовок, сжатие, проба квоты, поиск) шлюз
  отличает по заголовкам и телу: Claude Code — `x-claude-code-agent-id`, запрос без `tools` или только с
  `web_search`, хвост «REMINDER: Do NOT call any tools»; Codex — `x-openai-subagent`, `x-codex-parent-thread-id`,
  `x-codex-turn-metadata` (`request_kind` не `turn`, `thread_source` `subagent`/`thread_title`); Antigravity —
  `requestType: checkpoint`, запрос без `functionDeclarations` или с `complete_task`. Вызовы инструментов, лимиты и
  ошибки служебных запросов рассылаются как обычно; неразобранный запрос считается основным. Событие несёт вид
  запроса (основной, субагент с id, заголовок, сжатие, прочее); эпоху FUSE двигает только конец основного хода.
- Шлюз видит `tool_use` раньше, чем агент открывает файл, и даёт FUSE команду скачать его (предзагрузка тем же путём,
  каким откроет агент: проверка версии и watch те же). Предзагружают инструменты чтения по `path`: `Read`, `Edit`,
  `view_file`, `replace_file_content`, `read_file`, `replace`, `view_image`; запись нового файла — нет. Путь вне рабочего
  каталога, относительный, скрытый от агента или существующий в контейнере локально (временный файл агента) игнорируется, ошибка — только в журнал.
- Gemini разбирается с обёрткой Code Assist `{response, traceId}` и без; ответы без потока — у Messages API и
  `retrieveUserQuotaSummary` (Claude Code после двух оборванных потоков повторяет без `stream`).
- Ошибка соединения: 5 попыток, пауза 30 с, таймаут 10 с; затем 502 в формате Anthropic (у всех агентов), `warning`.
  Тело запроса > 64 МиБ — 413; ответ без потока > 4 МиБ не разбирается. Повтор — только если соединение упало до
  начала ответа; обрыв посреди потока отдаётся агенту.
- Заголовки запросов не пишутся в журнал (токен); прокси из окружения шлюз не использует.
- **Шлюз пассивен.** Тело — байт в байт; сквозные заголовки (включая `Accept-Encoding`) сохраняются, кроме
  hop-by-hop, `Host`, `Content-Length`. TLS, HTTP-версия и транспортные заголовки — шлюза, сервис не видит исходный
  сетевой запрос целиком. Ответ — потоком байт в байт; разбор — по своей распакованной копии (gzip, deflate, br,
  zstd), сбой или неизвестная кодировка лишают только событий. Отличия ClientHello шлюза от CLI измерены;
  применение их сервисами для санкций неизвестно — принятый риск. Заголовки `anthropic-ratelimit-unified-*` проходят
  без изменений.

### Инструменты агентов мимо runner

Встроенные инструменты не отключаются и не перехватываются глубже FUSE, оболочки и шлюза: что агент делает в своём процессе, остаётся в контейнере session. Решения по каждому случаю — принять как есть, с условиями.

- Claude Code, `ListAgents` и `SendMessage`: сокет `<каталог>/cc-socks/<pid>.sock` (каталог — `$XDG_RUNTIME_DIR`, иначе `$CLAUDE_CODE_TMPDIR`, иначе `/tmp`), список собеседников — реестр `$CLAUDE_CONFIG_DIR/sessions`. Сессия видна другой только при общем каталоге конфигурации и достижимом сокете; `SendMessage` вставляет текст в чужую сессию, при общем `/tmp` реестр затирается совпадающими pid разных контейнеров. У каждой session свой `/tmp` и свой каталог конфигурации; шаблон контейнера запрещает общий `/tmp` (`Binds`, `PidMode`, `IpcMode`, любой `Tmpfs` кроме `/work` и `/run/secrets`, любой `Mounts` кроме одного тома в каталог агента), это стерегут тесты шаблона. Каталог сокетов переменными не задаётся. Подагенты работают в процессе родителя без своих сокетов.
- Claude Code, снимок оболочки: его строит локальный bash (вызовы `-c env` и снимка идут не на runner); в снимке `find` и `grep` — функции на встроенные в бинарник `bfs` и `ugrep`, `rg` — на встроенный, если системного нет. На runner уходит только команда: функции снимка там не действуют, исполняются системные `find`, `grep` и `rg` runner (без `rg` на runner команда отвечает «command not found»; `grep` не обходит `.git` и бинарники сам). Подмена не отключается ни переменными, ни флагами. Подсказка про `rg` — при необходимости в правилах Iapetus.
- Antigravity, команды: `run_command` идёт как `bash -c` через `bash` из `PATH` — на runner. `run_workflow` запускает `python3` в контейнере мимо оболочки; `python3` в образе session нет, и инструмент отвечает отказом. `run_script` пишет `driver.py` в контейнер и запускает его через оболочку: на runner файла нет, вызов падает. Поиск и список каталогов (`grep_search`, `find_by_name`, `list_dir`) читают дерево через FUSE; `read_url_content`, `search_web`, `generate_image` ходят в сеть контейнера.
- Antigravity, каталоги и `git`: том состояния (`~/.gemini/antigravity-cli`) записываем для пользователя агента — без записи agy не стартует; `~/.cache/antigravity/bin` и `~/.gemini/antigravity-cli/bin` на запись не требуются (поиск идёт запасным путём, пропускается установка `webm_encoder`); `/opt/agy` только для чтения. `git` в образе нет: подагенты `share` и `branch` работают в общем каталоге. С `git` agy создавал бы ветки `subagent-…` и `git worktree` в репозитории runner через FUSE.
- Состав образа session: `git`, `python3` и `rg` не ставятся (`git` весит ≈114 МиБ вместе с `perl`). Файлы `/usr/bin/perl*` из `perl-base` (essential, без него не работают `dpkg` и `debconf`) удаляются последним шагом сборки: агенту и скриптам образа он не нужен, а был бы готовым сетевым клиентом; ставить пакеты в работающем контейнере после этого нельзя.
- Не снято: интерактивный TUI Claude Code в pty (сокет создаётся тем же кодом), вход в сокет пира, набор инструментов agy при входе аккаунтом Google, `git worktree` agy на FUSE-репозитории настоящего runner. Проверено на Claude Code 2.1.285 и agy 1.2.14 с поддельным API.

### MCP проекта

Runner — окружение агента, поэтому MCP-серверы проекта работают на нём, а не в контейнере. Работают серверы `stdio`, `http` (streamable HTTP) и `sse` из `.mcp.json`; подключается runner, OAuth не поддерживается — токен заголовком из окружения.

- Runner не MCP-сервер. При назначении пары он один раз читает `.mcp.json` рабочего каталога, запускает описанные там
  серверы у себя и по `initialize`, `tools/list`, `resources/list`, `prompts/list` собирает сводку: инструменты,
  ресурсы, prompts и `instructions` каждого сервера. Пока пара назначена, сводку получает server (`McpCatalog`) и
  сообщает её session; так server знает набор инструментов сессии сверх собственных. Правка `.mcp.json` в середине
  сессии вступает в силу после смены или перезапуска пары.
- Вызовы идут мимо server: session ↔ runner по каналу данных, шифротекст до session. Server видит только сводку.
- Session — второй MCP-сервер на localhost контейнера: показывает агенту инструменты, ресурсы и prompts с префиксом
  имени сервера и пересылает `tools/call`, `resources/read`, `prompts/get` runner. Агенту прописаны два MCP: server и
  session. Конфиги пишет session до запуска агента, как для MCP Iapetus.
- `instructions` серверов session дописывает в файл правил Iapetus; он обновляется при смене runner и `.mcp.json`.
- Обрыв канала данных во время вызова — ошибка агенту «связь оборвалась, результат неизвестен»; вызов не повторяется.
- MCP Iapetus на server и session отвечает 403 на запрос с заголовком `Origin`, даже пустым (его шлёт только
  браузер); session на пакет JSON-RPC (массив) — 400 и `-32600`, server (rmcp) — 415; batch не поддерживается.
- Сетевые серверы (`http`, `sse`) принимают `url`, `headers` и `headersHelper`: команда оболочки в каталоге проекта
  с окружением команд проекта и `CLAUDE_CODE_MCP_SERVER_NAME`/`_URL` печатает JSON «заголовок — строка»; таймаут
  10 с; запускается при каждом подключении и новой сессии; перекрывает одноимённые `headers`; значения маскируются.
  Ответ 401/403 — ошибка «сервер <имя> требует авторизации: задайте токен в `headers` через `${VAR}`» с
  `WWW-Authenticate` (журнал и ответ на вызов; сервер, не подключившийся при старте, в сводку не попадает). 404 на
  запрос с `Mcp-Session-Id` — новая сессия (helper, `initialize`) и один повтор; второй 404 — ошибка. Клиент
  объявляет `roots` без `listChanged`, на `roots/list` — `file://<каталог проекта>`, `ping` — `{}`, прочие запросы
  сервера — `-32601`; запросы сервера доходят по stdio, потоку SSE и внутри ответа на POST у streamable HTTP
  (GET-потока нет). Не делаются: `list_changed` и отмена вызова (прерванный вызов живёт на runner до 120 с) — не
  выбраны пользователем; `elicitation`, прогресс, OAuth — отложены; `sampling` — не поддерживается.

## waldo runner

- Окружение команды: server ← `.env` ← система (приоритет слева направо; в слое server свои ключи сильнее ключей
  родителя, они сильнее `all`). `.env` — из каталога запуска или по пути `IAPETUS_ENV_FILE`, перечитывается на
  каждой команде; слой server — подписка `Env`.
- Слой server хранит server (`all.VAR` для всех, `<fingerprint>.VAR` для одного, сильнее); пишет по запросам worker
  `Env.*`; runner получает снимок и изменения запросом `Env` (подробности — «Окружение и документы»).
- Снимок слоя; переподключение само (паузы 1–30 с), после обрыва — подписка заново и новый снимок. Нет свежего
  снимка — команда ждёт до 10 с, затем ошибка «переменные server недоступны»; старые значения не отдаются.
- Конец сессии для runner — server снял назначение: отмена команд сессии, снятие watch, убирание `GITHUB_TOKEN`,
  завершение клона.

## Протокол

- **Канал управления** — регистрация, присутствие, назначение, окружение, документы, состояние session, запросы
  worker к server: SSH к server, подсистема `iapetus-control`, внутри `nerve::mux`. **Канал данных** — SSH runner →
  назначенная session через jump: операции FUSE, команды, watch.
- Данные сессии (файлы, вывод команд) в канал управления не попадают: он оканчивается на server. Канал данных
  шифруется от runner до session, server видит шифротекст. Управление, окружение и `GITHUB_TOKEN` идут каналом
  управления — server для них доверенный.
- Сообщения — postcard в обоих каналах, типы в `nerve`. Первый кадр `nerve::mux` — версия (`nerve::protocol::VERSION`,
  сейчас 23, одна на оба канала; все программы выпускаются одной сборкой); несовпадение — кадр `version` и закрытие, узел пишет причину в журнал и повторяет не чаще раза
  в 30 с. Прочие ошибки — `Err` в ответе: путь вне рабочего каталога, нет файла, `NotEmpty`, конфликт записи, отказ в
  доступе, ошибка ввода-вывода с текстом.
- Канал управления равноправен, как `nerve::mux`: запрос получает один ответ или поток ответов, запросы идут в обе
  стороны. Набор запросов задан ролью соединения: у worker, runner и session свой `enum`; сообщение не из набора роли
  — ошибка разбора и закрытие соединения. Роль и fingerprint берутся из входа, сообщения их не несут (кроме
  `Register` и `Renew`).

### Вход на server

Один процесс SSH на `russh`, два слушателя: внешний (адрес Tailscale или ZeroTier) и внутренний (сеть Docker, порт
наружу не публикуется). Оболочки, `exec`, pty и пробросов, кроме `direct-tcpip` jump, нет.

| Слушатель | Логин | Метод | Кто | Что разрешено |
|---|---|---|---|---|
| внешний | `iapetus-enroll` | `password` — `orbit_key` | runner и worker без действующего сертификата | подсистема `iapetus-control`, только `Register`, `Renew`, `WorkerCertificate`; после ответа соединение закрывается, без запроса — через 10 с |
| внешний | `iapetus-control` | сертификат | runner, worker | подсистема `iapetus-control`, набор запросов роли |
| внешний | `iapetus-jump` | сертификат | runner, worker | `direct-tcpip` в session по маршруту реестра (jump) |
| внутренний | `session-<fp>` | `password` — секрет session | session | подсистема `iapetus-control`, набор запросов session |

- **Роль** — по `key_id` сертификата, подписанного CA server: у worker — служебное значение (не fingerprint), иначе
  fingerprint runner (закреплён за ключом узла). Принципалы runner: `iapetus-control`, `iapetus-jump`, `iapetus-data`;
  worker — `iapetus-control`, `iapetus-jump` и `name` (вход в session). Имя worker, начинающееся с `iapetus-`, server
  отвергает при выдаче сертификата. Pty не разрешён ни одному принципалу, кроме `name` worker (`permit-pty`).
- **Ключ хоста** — Ed25519, создаётся при каждом запуске server и общий для обоих слушателей. Хост-сертификат (`key_id`
  `orbit-server`, принципалы — `--host`, срок год от запуска) подписан CA: клиенты верят CA, поэтому смена ключа хоста
  при перезапуске их не касается.
- **`password`, а не keyboard-interactive:** секрет один, диалога нет, клиент `russh` отправляет его сам. Клиент
  отправляет пароль только после проверки хост-сертификата server по CA (`orbit_ca`): без него — отказ, пароль не
  уходит. Отказ — с паузой 1 с; до входа соединение живёт 10 с.
- Внутренний слушатель не принимает логинов узлов, внешний — `session-<fp>`: session недоступна из сети пользователя,
  узлы недоступны из контейнеров. Секрет session — файл на её `tmpfs`, значение при создании контейнера выдаёт
  server.
- Session входит на server тем же способом, что узлы: клиент проверяет хост-сертификат server по CA (открытый ключ в
  образе session).
- Keepalive SSH 5 с × 3 на обеих сторонах и в обоих каналах (короче — ложные обрывы). Канал управления и jump —
  отдельные TCP-соединения: передача файла по jump не задерживает keepalive и запросы управления.

### Узлы

- Человек нигде не регистрируется. Узлу задают `orbit_url` (адрес SSH server, `хост:порт`: управление и jump; хост из
  него — имя, которое проверяется по принципалам хост-сертификата server), `orbit_ca` (открытый ключ CA), `orbit_key`
  (секрет одной строкой, без частей), `name` (по умолчанию — локальный пользователь). Runner читает их из
  `--orbit-url`, `--orbit-ca` (путь к файлу), `--orbit-key`, `--name` или из `IAPETUS_ORBIT_URL`, `IAPETUS_ORBIT_CA`,
  `IAPETUS_ORBIT_KEY`, `IAPETUS_NAME`; worker — только из файла настроек.
- Runner: fingerprint (uuid4) и ключ Ed25519 (`0600`, закрытая часть не покидает машину) создаются при первом запуске.
  Каталог личности: fingerprint, ключ, сертификат, `orbit_key` (`0600`, шире — отказ); по умолчанию
  `$XDG_STATE_HOME/iapetus/runner/<имя каталога>-<16 hex sha256 канонического пути>` (`IAPETUS_IDENTITY_DIR`);
  `--name` личность не меняет; второй процесс на каталог — отказ (`flock` на `lock`).
- Клон (`--temporary`) без `--identity-dir` не стартует; родитель даёт каталог `<своя личность>/clones/<имя>-<N>` и кладёт туда `orbit_key`; автор коммитов хранится там же файлом `author`; при гибели клон удаляет
  свои файлы и каталог.
- `orbit_key` из переменной или `--orbit-key` runner сохраняет в каталог личности и перезапускает себя (`execve`) без
  них: в `environ` и `cmdline` его нет.
- **Регистрация.** Runner входит как `iapetus-enroll` и шлёт `Register`: fingerprint, открытый ключ, имя, ОС, у клона —
  fingerprint родителя (родитель зарегистрирован, не отозван и сам не клон, иначе отказ; имя клона не уникально —
  личность узла задаёт fingerprint). Server запоминает ключ, отвечает сертификатом на 15 минут (в реестре — выдача и срок
  последнего, истории нет; входы — в журнале; сертификат хранит runner); runner закрывает соединение и входит по
  сертификату.
- **Продление.** Runner за 5 минут до истечения шлёт `Renew` по своему каналу управления; после истечения (в том числе
  с выключенной машины) входит как `iapetus-enroll` и шлёт тот же запрос. Запрос несёт `orbit_key`, время и подпись
  ключом узла; подпись покрывает время, окно ±5 минут. Любой сертификат — только по действующему `orbit_key`. Чужой
  fingerprint без закрытого ключа не присвоить. Не продлённый сертификат — server закрывает канал управления в
  момент `valid_before`.
- **Worker** при запуске создаёт одноразовый ключ, входит как `iapetus-enroll` и шлёт `WorkerCertificate` (открытый
  ключ, `name`); получив сертификат на 15 минут, открывает канал управления и jump по сертификату. Продлевает так же,
  как runner: `WorkerCertificate` с `orbit_key` по каналу управления, после истечения — через `iapetus-enroll`.
  Личности у worker нет.
- **Новый `orbit_key`** сразу закрывает каналы управления и туннели jump всех worker и всех runner: сертификаты,
  выданные раньше, не пускают, связь session с runner и worker обрывается, session остаётся ждать (`warning`, runner
  пропал). Runner с прежним ключом получает `Access` при продлении и завершается. Выдавший worker тоже отключается: TUI
  показывает новый ключ один раз, человек вписывает его в файл настроек всех worker и запускает их заново.
- **Отзыв runner** (из TUI): пометка в реестре, запись остаётся; клоны отзываются вместе с родителем (та же машина); server закрывает канал управления и туннели jump
  runner, не продлевает сертификат, отказывает в `Register` и `Renew` того же ключа и fingerprint (`Access`); jump
  проверяет пометку на каждом туннеле; session закрывает канал данных. Runner, получивший `Access` при продлении,
  завершается. Если `orbit_key` мог остаться на машине — выдаётся новый. Отдельный worker отозвать нельзя (нет
  личности): все сразу — новым `orbit_key`.
- Server сверяет сертификаты и пометки реестра на каждом входе и туннеле; отдельной службы доверия нет.
  Узлы друг друга не видят: runner и worker говорят только с server, session задач runner не шлёт, runner принимает
  запросы только от server.

### Присутствие и переподключение

- Runner в сети — пока открыт его канал управления. Соединение одно на fingerprint: новое вытесняет прежнее. Нет
  канала — 📴. Закрытие TCP видно сразу, молчание — по keepalive (≈15–20 с, не измерено). Присутствие хранится в
  памяти server: после запуска все runner 📴, пока не подключатся. Назначение 📴 не снимает. Конец назначения подтверждает `End`: пока runner его не подтвердил, он 🔒.
- Session — не присутствие, а состояние: server хранит последний `Status`, жив ли контейнер видно по Docker.
- Клиент (runner, worker, session) переподключается сам: паузы 1–30 с с удвоением и разбросом, вход по сертификату;
  сертификат истёк или вход отклонён — `iapetus-enroll` и `Renew`. Ответ `Access` (отзыв, новый `orbit_key`) —
  runner завершается с ошибкой, worker просит новый `orbit_key`; прочие отказы и нет сети — повтор.
- Обрыв закрывает ожидающие запросы ошибкой `Closed`. Очереди сообщений нет: что было состоянием, server и клиент
  вычисляют заново при подключении.

| Сообщение при обрыве | Что происходит |
|---|---|
| запрос worker: чтение, список, `Env`, переименование, назначение, смена ключа, завершение, перезапуск | идемпотентны; клиент повторяет один раз после переподключения |
| `Sessions.Start`, `Runners.Clone`, `Nodes.NewOrbitKey` | не повторяются: ошибка в TUI; результат видно в списке (новый `orbit_key` — ответ приходит один раз, при потере выдаётся новый) |
| server → runner `Clone` | не ставится в очередь: ошибка «runner не в сети» |
| server → runner `Session` | состояние, не команда: после каждого подключения runner server шлёт `Start` (назначена) или `End` (нет); `Start` для идущей сессии — `Ok` без действий |
| server → session `Control` | после каждого подключения server шлёт `AssignRunner` с текущим назначением |
| session → server `Status` | первое сообщение после подключения — полное состояние (`Hello`) |
| `Env`, `Docs` (подписки runner и session) | подписка заново, первым — снимок |

- Обрыв канала управления не завершает сессию, команды и клон: каналы данных отдельные; runner без канала
  управления — 📴 и session в `warning`. Конец сессии, случившийся во время обрыва, доходит `End` после
  подключения.
- Запуск server: реестр и назначения — из SQLite; узлы подключаются сами, session получает `AssignRunner`, runner —
  `Start`.

### Канал управления

**Runner → server**

| Запрос | Что |
|---|---|
| `Host` | первый запрос канала управления: `RunnerHost` (путь проекта, hostname, `$HOME` ≤ 4096 байт, `os_release` ≤ 16 КиБ); повторный — `Conflict`. Runner в сети только после него; server хранит окружение в памяти и после отключения runner, назначенной session шлёт `AssignRunner` при первом `Host` и при смене окружения |
| `Register` | первая регистрация (только `iapetus-enroll`): fingerprint, ключ, имя, ОС, родитель → сертификат |
| `Renew` | продление: `orbit_key`, fingerprint, время, подпись ключом узла → сертификат |
| `McpCatalog` | сводка MCP-серверов проекта (имя, инструменты, ресурсы, prompts, `instructions`), пока runner назначен session; пустая сводка заменяет прежнюю и, как любая, отдаётся session при подключении |
| `Env` | подписка: поток ответов — `Snapshot` (слои `all`, родителя, свои), затем `Set`, `Delete` до закрытия соединения |

**Server → runner**

| Запрос | Что |
|---|---|
| `Clone` | временный клон в каталоге (по запросу session или worker) → fingerprint, имя; таймаут 60 с |
| `Session::Start` | начало сессии: номер назначения, «можно подключаться», автор коммитов, `GITHUB_TOKEN` → `Ok` |
| `Session::End` | конец сессии с номером назначения → `Ok`; `End` с чужим номером игнорируется |

**Session ↔ server** (внутренний слушатель)

| Запрос | Направление | Что |
|---|---|---|
| `Hello` | session → server | первое сообщение: полный `Status` |
| `Status` | session → server | при каждой смене: состояние, причина (текст `reason` и вид `cause`), время сброса лимита (`limit_reset`), окна подписки (`limits: Vec<UsageWindow>` — длина окна, область — модель или вся подписка, израсходованная доля 0..1, время сброса; последние окна, которые шлюз разобрал из заголовков ответа API, 2xx и 429: Claude Code — `anthropic-ratelimit-unified-<окно>-utilization` и `-reset` (`5h`, `7d`, `7d_<модель>`; служебные `overage`, `7d_oi` пропускаются), Codex — `x-codex-{primary,secondary}-used-percent`, `-window-minutes`, `-reset-at`, Antigravity окон не сообщает — список пуст; список заменяется целиком при ответе с окнами и переживает перезапуск агента), runner, занятость, `agent_running` |
| `Docs` | session → server | подписка: поток — `Snapshot` (имя, содержимое), затем `Updated`, `Removed` |
| `Control` | server → session | `AssignRunner` (runner и действие над агентом: оставить, остановить, перезапустить с `resume` или чисто; `None` — снять), `Resume` (перезапуск с продолжением разговора в конце основного хода; повторный `Resume`, пока первый ждёт, — сразу, с обрывом хода), `UpdateAgent` (агент, версия, артефакты: платформа, URL, хеш, формат; обновление ждёт, пока нет worker и хода) |

**Worker → server**

| Запрос | Что |
|---|---|
| `WorkerCertificate` | сертификат SSH на одноразовый ключ; несёт `orbit_key` (`iapetus-enroll` или канал управления) |
| `Sessions.*` | список; поднять (агент, runner; поток ответов: агент запущен — можно входить; сессия завершена); завершить; перезапустить из `failure` (`Restart`); перезапустить работающего агента (`RestartAgent` → session `Resume`; не в сети — `Error::Io`) |
| `Runners.*` | список (имя, fingerprint, 🔓 🔒 📴, временный ли), назначить (runner и `resume`), переименовать, создать клон |
| `Nodes.*` | список runner, отзыв, новый `orbit_key` |
| `Env.*` | окружение: ключи по runner и `all`, записать, удалить |

- Server отвечает worker о `Sessions.Start` потоком: агент запущен — один ответ, дальше поток держится до конца
  сессии.
- Назначение session: server проверяет, что runner 🔓 (в сети и свободен), поднимает контейнер, session подключается и
  получает `AssignRunner`, runner получает `Start`; назначение пишется в реестр (SQLite) и переживает перезапуск
  server. Клон: `Runners.Clone` (worker) или MCP `runner_clone` (через server напрямую) → server проверяет runner в реестре и в сети,
  шлёт ему `Clone`, возвращает ответ.

### Окружение и документы

- **Окружение** хранит server в SQLite: ключи `all.VAR` для всех, `<fingerprint>.VAR` для одного (сильнее). Ключ иного
  вида — отказ. Значения шифруются тем же ключом, что токен GitHub, и в журнал не пишутся. Пишет server по
  запросам worker `Env.*`, через них же worker читает.
- Runner получает через `Env` только слои, которые ему положены: `all`, родителя (у клона) и свои; чужие ключи не
  видит. Каждая запись реестра — рассылка `Set`/`Delete` подключённым runner, которым слой относится. Приоритет у
  runner: свои, родителя, `all`. Подписчик, не успевающий читать рассылку, отключается и подписывается заново.
- **Документы** — общие документы для правил Iapetus: файлы `*.md` в каталоге `docs/` рядом с состоянием server,
  кладёт и меняет человек на хосте server; worker их не пишет. Server рассылает изменения подписанным session
  (`Docs`); читает только session. Документ — не больше 1 МиБ, в UTF-8; имя документа — имя файла вместе с `.md`.

### Канал данных

- **Порядок.** (1) Worker выбирает сессию и runner, server назначает. (2) Runner получает по каналу управления `Session::Start`
  («можно подключаться»), входит на jump (`iapetus-jump`) своим сертификатом (адрес один), server перенаправляет
  поток в session. (3)
  Связь есть — session запускает агента в pty. (4) Агент запущен — server отвечает worker, и только тогда worker
  может войти.
- **Без уведомления — отказ:** runner без назначения и worker, чья сессия не разбудила агента, получают отказ и
  закрытие. Jump даёт только `direct-tcpip`: ни shell, ни команд, ни иных каналов.
- Внутри SSH один канал с фреймингом: кадры `длина | id | флаги | тело` по 16 КиБ, сообщения чередуются по кругу.
  Окно SSH 8 МиБ. Канал на запрос не используется (вдвое медленнее, падает на тысячах). Хранилища для данных не нужно.
- **Пара один-к-одному.** Server сообщает session fingerprint назначенного runner; принимается только он, новое
  соединение вытесняет старое; смена runner — закрытие текущего. Срок сертификата проверяется при входе, поэтому отзыв
  — закрытие соединения.
- Session — SSH-сервер (`--data-listen`, по умолчанию `0.0.0.0:2222`; только вход по сертификату). Runner входит под
  `iapetus-data`: отдельный пользователь и принципал, без shell, `exec`, pty — только подсистема канала данных. Worker
  входит под своим `name` (см. «Вход через TUI worker»). Runner проверяет хост-сертификат session по CA server. Jump
  ведёт на адрес, с которого session подключилась к внутреннему слушателю, и порт 2222: другой `--data-listen` jump не
  находит.
- Keepalive SSH 5 с × 3 на обеих сторонах и на jump (короче — ложные обрывы). Обрыв — явная ошибка. После
  переподключения (свой таймаут на попытку) runner шлёт `Unwatched` по всем каталогам.
- Потерян ответ на `Write`, `Rename` или `Remove` (обрыв канала или таймаут): session ждёт канал и узнаёт результат
  по состоянию runner (`Hash`, `Stat`), журнала операций нет. `Write`: новое содержимое записано — выполнено, ожидаемое
  старое — повтор, иное — конфликт. `Rename`: цель с хешем источника и источника нет — перенесено; как ожидалось —
  повтор; иное — конфликт. `Remove`: пути нет — удалено; файл с тем хешем, что видел агент, — повтор; иное — конфликт.
  Отказ повтора (`Conflict`; у `Rename` ещё `NotFound`, у `Remove` — только `NotFound`) не доказывает, что первая
  попытка не удалась, поэтому сверка идёт заново, всего три попытки. Итог команды — `Attach`: остаток вывода с первого
  не полученного сообщения (heartbeat в счёте).

### Файловые операции

- Пути — относительно рабочего каталога runner (FUSE монтируется по тому же абсолютному пути, cwd совпадает).
  Runner разрешает путь строго внутри каталога (`openat2` с `RESOLVE_BENEATH` или эквивалент): `..` и ссылки наружу —
  ошибка. Граница — только для файловых операций: команды идут от пользователя runner без песочницы и видят всё,
  включая ключ узла.
- `Stat` (вид, размер, mtime, права); `ReadDir` (записи с атрибутами и `watched`); `Read` (файл целиком с sha256);
  `Hash` (sha256 и атрибуты без содержимого); `Write` (содержимое и ожидание «хеш версии»/«не существует», под
  блокировкой пути: временный файл, `fsync`, `rename`; несовпадение — конфликт); `Rename` (хеш источника и ожидание
  цели: `renameat2`, `RENAME_NOREPLACE` при «не существует», только обычные файлы, блокировки `(dev, inode каталога,
  имя)` в отсортированном порядке, `fsync` обоих каталогов); `MakeDir`; `Remove` (файл, сама ссылка или пустой каталог
  под блокировкой имени; непустой — `NotEmpty`). Хеш — sha256 содержимого.
- Запросы и пакеты наблюдения несут корень `Root::{Project, Home}` (`DataRequest::Fs { root, request }`,
  `WatchBatch { root, changes }`), пути — от каталога корня. Runner без отдачи `$HOME` отвечает на `Home` `OutsideWorkdir`.
- Символические ссылки видны ядру ссылками (`Kind::Symlink`, атрибуты самой ссылки); `readlink` — запрос
  `ReadLink { path }` → `Link(цель)`, по ссылке идёт ядро. Runner отдаёт цель как записана, если после разрешения от
  каталога ссылки (канонический путь, ссылки по дороге учтены) она внутри рабочего каталога или `$HOME` runner;
  висячая ссылка внутри проекта отдаётся; иначе — `Access` (`EACCES`): ядро разрешило бы цель в файловой системе
  контейнера и показало бы чужой файл. Session кэширует цель на эпоху вместе с атрибутами ссылки: замена ссылки
  меняет атрибуты, и событие watch обесценивает цель.

### Изменения на runner

- Runner следит за каталогами, прочитанными через `ReadDir`, и шлёт пачки `WatchBatch`: `Updated` (путь, атрибуты как
  в `Stat`), `Removed`, `Unwatched`; применяются по порядку и обновляют кэш метаданных FUSE.
- Только прочитанные каталоги (рекурсивный watch в `node_modules`/`target` упирается в лимиты inotify). inotify — через
  `rustix`, без `unsafe`; подписка ставится до чтения записей; повторный `ReadDir` не дублирует. Следят за
  появлением, удалением, переименованием, содержимым и атрибутами; inotify только отмечает пути, атрибуты — `stat`
  после окна склейки 30 мс (серия записей — один `Updated`); на событие в каталоге уходит и `Updated` самого каталога.
- `Removed` каталога — удалено поддерево. Удалён и создан заново — `Removed`, затем `Updated`. Переименованный каталог
  теряет подписки под старым именем.
- `Unwatched` — кэшу каталога верить нельзя до нового `ReadDir`. Причины: `max_user_watches` (`ENOSPC`) и любая ошибка
  `inotify_add_watch`; переполнение очереди (все каталоги); `IGNORED`; каталог удалён до подписки; достигнут через
  ссылку; ошибка атрибутов записи. Атрибуты ненаблюдаемого каталога на размер и mtime не обновляются.
- Конец сессии снимает подписки и отбрасывает неотправленное.

### Команды

- Оболочка — тонкий клиент агента: команду передаёт агенту через unix-сокет (`0600`, владелец — пользователь агента),
  агент шлёт её на runner. Тот же бинарник, что агент, по ссылке `/opt/iapetus/bash` (`argv[0]` на `bash` включает
  режим оболочки). Служебные вызовы — локальному `/bin/bash`; не совпавший с шаблоном вызов отклоняется ошибкой
  (иначе выполнился бы в контейнере). Claude Code (2.1.288) дописывает ` < /dev/null` после `eval <команда>`, кроме команд
  со своим вводом (`<` или heredoc) — такой вызов без него принимается только при вводе в самой команде. Каналы управления и данных и секрет узла — только у агента от root.
- Команда: id, текст, cwd. Таймаут соблюдает Claude Code, завершая оболочку — это `cancel`; запрос несёт и свой `timeout_ms`, по нему runner убивает группу так же, как по `cancel`. После каждой команды, в
  том числе неудачной, агент начинает новую эпоху FUSE до ответа оболочке.
- Runner: `bash -c` в своей группе процессов, stdin `/dev/null`; `pwd -P` пишет ловушка на выходе в дескриптор,
  открытый до команды (доходит при `exit` и своей `EXIT`). cwd — внутри рабочего каталога, `..` и выход отклоняются.
  Повторный известный id отдаёт поток той же команды (завершённая — сохранённый итог), заново не запускается; отмена
  — только id из журнала своей сессии, иначе `NotFound`; `Attach` неизвестного id — «runner перезапущен, итог неизвестен».
- Окружение очищается: переменные сессии ← слой server ← `.env` ← снимок окружения runner при запуске без `IAPETUS_*` (приоритет слева
  направо). Без начавшейся сессии — без `GIT_*` сессии.
- Секрет — переменная `TOKEN`, `KEY`, `SECRET`, `PASSWORD` или на `_TOKEN`, `_KEY`, `_SECRET`, `_PASSWORD` (без учёта
  регистра), во всех слоях. Значения из всех слоёв в выводе заменяются на `***` в обоих потоках, включая разорванные
  границей кусков; короче 4 байт не маскируются; секрет внутри другой переменной (пароль в `DATABASE_URL`) не виден.
- Ответ потоком: куски stdout/stderr (оболочка пишет в один файл задачи), в конце код выхода или сигнал и cwd
  (`pwd -P`). После кода 0 оболочка пишет cwd в файл, откуда Claude Code берёт каталог. Heartbeat раз в 30 с;
  молчание дольше двух интервалов — «runner пропал».
- SIGINT/SIGTERM оболочке — `cancel`: SIGTERM группе, через 2 с SIGKILL; конец сессии отменяет команды. Обрыв связи
  команду не отменяет: дорабатывает, итог забирается после переподключения. Повторно команда не запускается; отменить
  может только запустивший. Фоновые процессы, пережившие команду, живут, пока session на связи; после выхода bash вывод
  дочитывается до 2 с. Порядок stdout/stderr приблизителен.
- Конец назначения убивает группы всех команд и потомков runner, ушедших из группы. Session не вернулась к runner за
  5 минут после обрыва канала данных — runner завершает процессы всех её команд (SIGTERM группам, через 2 с SIGKILL)
  и ушедших из группы (`setsid`, двойной fork): каждая команда запущена с `IAPETUS_COMMAND=1`, по этой метке они
  находятся среди потомков runner; проектные MCP-серверы и клоны не затрагиваются. Назначение и итоги команд остаются;
  вернулась раньше — ничего не убивается, отсчёт при следующем обрыве заново. Процесс, сбросивший метку, достаёт
  группа команды, пока он из неё не вышел.
- id уникален в паре (отправитель, назначение). Итог хранится в памяти до конца сессии (после выдачи повтор получает «итог команды уже передан»): ≤ 64 МиБ вывода на
  команду и 256 завершённых команд, вытесненный — «вывод команды вытеснен из журнала runner»; после перезапуска runner — «runner перезапущен, итог неизвестен». `cancel`
  — только от того же отправителя.
- При остановке runner шлёт SIGTERM потомкам (кроме клонов и их потомков), через 2 с SIGKILL; runner — subreaper
  (`PR_SET_CHILD_SUBREAPER`). Клон — отдельный runner: родитель запускает его в своей группе процессов и при
  остановке не убивает.
- Супервизор: `waldo runner` без служебного признака `--supervised <pid>` сохраняет `orbit_key` в каталоге личности,
  освобождает его и запускает настоящий runner (`/proc/self/exe` с теми же аргументами) дочерним процессом. Супервизор —
  тоже subreaper: если runner убит (SIGKILL), он завершает осиротевших потомков команд, кроме клонов. Убит супервизор —
  runner получает SIGTERM (`PR_SET_PDEATHSIG`) и останавливается штатно.

## Доступ и авторизация

- Вход на server — по таблице «Вход на server»: runner и worker — сертификат от CA server (`orbit_key` — только для
  регистрации и выдачи сертификата), session — секрет на внутреннем слушателе. Права разные: runner — запросы runner,
  session — запросы session, worker — запросы worker; чужое сообщение закрывает соединение. Runner принимает запросы
  только от server, session задач runner не шлёт, worker обращается только к server.
- Server — CA SSH: runner — сертификат на ключ узла (продление каждые 15 минут), worker — короткий на одноразовый
  ключ. Session доверяет только подписи server. Отзыв — только runner по fingerprint; worker — все сразу новым
  `orbit_key`.
- SSH server (оба слушателя) и session — на `russh`: он сам проверяет подпись сертификата ключом из сертификата и окно `valid_after`/
  `valid_before`; остальное — наш код при каждом входе: отпечаток CA совпадает с ключом server (`validate_at`), тип —
  user, срок конечен и не больше допустимого, принципалы непусты и содержат имя входа, critical options пусты. Вход
  по ключу без сертификата отклоняется.
- Server подписывает и host-сертификаты — своего SSH (jump и канал управления) и каждой session (ключ хоста и сертификат на год с принципалом `iapetus-session` server создаёт при каждом запуске
  контейнера и передаёт значениями в его окружении); клиенту хватает `@cert-authority`. Куда перенаправить, решает server по реестру:
  runner — в назначенную session, worker — в выбранную, когда агент запущен; иначе отказ.
- Вход в агента — вручную: session запускает агента без учётных данных, пользователь подключается к его pty через
  worker и входит сам (Claude Code — `/login`, Codex — `codex login --device-auth`, Antigravity — вход Google).
  Учётные данные остаются в томе состояния session (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, каталог agy) и переживают
  пересоздание контейнера; server их не хранит, не получает и не передаёт. Каждая session входит отдельно: у Codex
  копии `auth.json` гасят друг друга, у agy новый refresh-токен на каждый вход (лимит 100).
- 401 и 403 от сервиса — состояние `waiting` «нужен вход»: пользователь подключается к session и входит заново.
- Риск хранения чужих учётных данных на server снимается. Остаются риски Anthropic и Google: вход пользователя в
  немодифицированный агент внутри контейнера с пассивным шлюзом в сетевом пути (`RISKS.md`); Antigravity — условия
  называют доступ через стороннее ПО нарушением и допускают закрытие аккаунта, сочетание `agy`, шлюза, FUSE и
  контейнера не квалифицировано.
- Автоматической выдачи учётных данных в коде нет: убраны ключи агентов (реестр и TUI), `Keys.*`, одноразовый билет и
  `Ticket`, `Credentials`, `CLAUDE_CODE_OAUTH_TOKEN` из файла. Миграция реестра убирает ключи и сохранённые учётные
  данные, session остаются; шифр остался для значений окружения и токена GitHub.
- Подробности — `AUTH.md`.

## Обновление агентов

Обновляется Claude Code; Codex и Antigravity ставятся в образ точной версией и меняются пересборкой образа.

- Обновляет только server: он находит новую версию, проверяет её и сообщает session; session ставит её сама. Версию на
  свой вкус session не выбирает.
- Наблюдатель общий: по одному на каждого агента с источником выпусков в профиле server (в первом релизе — только
  Claude Code; у Codex и Antigravity источника нет, версия в образе точная). Ниже — источник Claude Code.
- Server раз в час читает канал `stable` (`downloads.claude.ai/claude-code-releases/stable`) и манифест этой версии.
  Подпись манифеста (`manifest.json.sig`, отделённая PGP) проверяется ключом Anthropic, отпечаток которого
  (`31DD DE24 DDFA B679 F42D 7BD2 BAA9 29FF 1A7E CACE`) записан в server; контрольная сумма бинарника платформы
  берётся только из проверенного манифеста. Версия, которая не новее предложенной прежде, не предлагается. Подпись не
  сошлась или манифест не разобран — версия не предлагается, причина в журнале. Платформа без записи или с
  некорректной sha256 пропускается с предупреждением, версия предлагается с оставшимися; без единой валидной
  платформы не предлагается.
- Срок и отзыв ключа подписи не проверяются (решение пользователя): вшитый ключ без срока, канала отзыва Anthropic
  не даёт; смена или отзыв ключа — новый выпуск orbit с другим ключом.
- Задержка (решение пользователя): server записывает в реестр (`agent_versions`), когда впервые увидел версию в
  канале, и предлагает её, когда она пробыла там не меньше `--update-delay` (по умолчанию 3 суток, 0 — сразу):
  плохой выпуск, ломающий перехват, поставщик обычно снимает за несколько дней. Манифест с подписью запрашивается
  только по истечении задержки; у более новой версии свой отсчёт; снятая из канала не предлагается; время первого
  появления переживает перезапуск server. Пробный запуск новой версии
  на session с откатом (канарейка) отложен до живого e2e на настоящем Claude Code.
- Предложение — `Control::UpdateAgent(AgentRelease)`: агент, версия и артефакты (`Platform`, URL, `Digest` —
  sha256 или sha512, `ArtifactFormat` — бинарник или tar.gz). Server шлёт его каждой session этого агента при выходе версии и при каждом её подключении (контейнер пересоздан — образ снова со старой
  версией, и session обновляется заново).
- Session отказывает обновлению чужого агента («обновление для другого агента») и агента без обновления в профиле
  («session не обновляет своего агента»). Берёт артефакт своей платформы; в первом релизе принимает только бинарник
  с sha256 по `https://`, sha512 и tar.gz (заготовка для Codex и Antigravity) отвергает. Скачивает бинарник по URL
  из предложения, сверяет хеш, кладёт его root-владельцем рядом с
  установленным и заменяет атомарным `rename`; пользователь агента заменить его не может. Совпала с установленной —
  ничего не делает.
- Обновление не прерывает человека и ход агента: пока к session подключён worker (зритель терминала) или идёт основной
  ход, версия ждёт; когда worker ушёл и ход закончился, session сама останавливает агента планово (не `failure`),
  заменяет бинарник и запускает агента с `resume` — так же, как при смене runner. Пока ждёт, новое предложение заменяет
  прежнее.
- Перезапускается только агент: пара с runner и канал данных не меняются, runner перезаходить не нужно. Если канал
  данных к этому времени оборван, его восстанавливает обычный путь: server сообщает runner о паре при каждом
  подключении.

## Репозиторий

Cargo workspace из трёх крейтов: общий `Cargo.lock`, версии в `[workspace.dependencies]`, lint'ы в
`[workspace.lints]`.

| Каталог | Что в нём |
|---|---|
| `nerve/` | Библиотека, общая для программ: протокол и сообщения каналов, мультиплексор (`mux`), правила сертификатов SSH (`ssh`), вход к orbit (`connect`): `connect::server` — клиент канала управления (три входа, переподключение, продление), `connect::session` — SSH через jump к session (`link`, канал данных), `connect::certificate` — срок сертификата, `OrbitKey`; fingerprint, состояния сессии, запуск процесса (`process`: журнал в stderr или в файл, runtime, сигнал остановки) |
| `orbit/` | Программа (только бинарь) и `Dockerfile` (стадии `server`, `session`); домены — модули `server`, `session` |
| `waldo/` | Программа (только бинарь) и `Dockerfile` (образ runner); домены — модули `worker`, `runner` |
| `docker/` | `docker-compose.dev.yml` — разработка; `docker-compose.test.yml` — проверки в сети без выхода наружу, итог — код выхода `check`; `apparmor/iapetus-session` |

- Тесты крейта — в `tests/` зеркалом `src/`. Каталога `tools/` нет.
- Контекст сборки образов — корень; `.dockerignore` не пускает `target/` и `.claude/`. Зависимости — отдельным слоем
  (cargo-chef, готовый бинарь со сверкой sha256; ключ слоя — `Cargo.toml` и `Cargo.lock`), затем `COPY . .` и сборка
  крейтов. Кэш-монтирований нет: общий `target` подсовывал cargo бинари другой копии.
- Образ `check` — без инкрементальной сборки и отладочной информации; `check-privileges` берёт готовый `check`.
